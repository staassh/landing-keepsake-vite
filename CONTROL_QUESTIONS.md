# Відповіді на контрольні запитання (Лабораторна робота №9)

### 1. Чим відрізняються `dependencies` і `devDependencies`? Чому `sass`, `vite` і лінтери мають бути саме в `devDependencies`?

- `dependencies` — пакети, необхідні для роботи застосунку безпосередньо під час виконання у продакшні (наприклад, бібліотеки фронтенд-логіки в браузері або серверні залежності).
- `devDependencies` — інструменти, які потрібні **лише на етапі розробки та збірки** (компілятори, бандлери, лінтери, оптимізатори картинок).
- `sass`, `vite`, `autoprefixer`, `prettier` і `stylelint` перетворюють вихідний код (`.pug`, `.scss`) на звичайні статичні файли (`index.html`, `.css`). У браузер користувача потрапляє вже готовий результат у `dist/`, тому в продакшні ці інструменти не потрібні.

### 2. Яку роль відіграє `package-lock.json` і чому його комітять, а `node_modules` — ні? Що робить `npm ci` і чим він відрізняється від `npm install`?

- `package-lock.json` фіксує точне дерево версій та хешів усіх встановлених пакетів і підзалежностей, гарантуючи відтворюваність збірки на будь-якому комп'ютері та в CI/CD.
- `node_modules` містить тисячі файлів і сотні мегабайтів коду, який легко відновлюється за `package-lock.json`, тому зберігати його в Git недоцільно.
- `npm ci` (_Clean Install_) видаляє наявну папку `node_modules` і встановлює пакети **суворо** за `package-lock.json` без його зміни (якщо є розбіжність із `package.json` — видає помилку). `npm install` може оновлювати версії в межах діапазонів (`^`, `~`) і перезаписувати `package-lock.json`.

### 3. Що означають записи `^7.1.7` і `~7.1.7` у `package.json`?

За стандартом SemVer (`MAJOR.MINOR.PATCH`):

- `^7.1.7` (каретка) — дозволяє автоматично оновлювати **мінорні та патч-версії** в межах поточного мажору: `>=7.1.7 <8.0.0`.
- `~7.1.7` (тильда) — дозволяє оновлювати **лише патч-версії** (виправлення багів) у межах поточної мінорної версії: `>=7.1.7 <7.2.0`.

### 4. Чим препроцесор відрізняється від постпроцесора? Наведіть приклади кожного з вашого проєкту.

- **Препроцесор** додає власний розширений синтаксис (змінні, цикли, міксини, наслідування) і компілює його у стандартний HTML або CSS. Приклади в проєкті: **Pug** (генерує HTML) та **Sass/SCSS** (генерує CSS).
- **Постпроцесор** приймає вже валідний CSS і трансформує його за допомогою плагінів (додає префікси, мініфікує, оптимізує). Приклад у проєкті: **PostCSS** із плагіном **Autoprefixer**.

### 5. Чим відрізняються `include` і `extends` у Pug? Як працюють `block`, `append` і `prepend`?

- `include` просто вставляє вміст одного Pug-файлу в інший у вказаному місці (використовується для секцій, шапки, футера).
- `extends` реалізує **наслідування шаблонів**: сторінка бере базовий макет (`layouts/main.pug`) і заповнює його іменовані слоти (`block`).
- `block name` повністю замінює вміст блоку макета; `block append name` додає код **у кінець** існуючого блоку макета; `block prepend name` додає код **на початок** блоку макета.

### 6. Як передати в Pug-міксин вкладений вміст і довільні атрибути? Покажіть на прикладі зі свого проєкту.

- Вкладений вміст передається через ключове слово `block` усередині тіла міксина, а довільні HTML-атрибути — через `&attributes(attributes)`.
- Приклад із `src/mixins/btn.pug`:
  ```pug
  mixin btn(label, href = "#contact", variant = "primary")
    a(class=["btn", `btn--${variant}`] href=href)&attributes(attributes)
      if block
        block
      span= label
  ```
  Виклик: `+btn('Contact us', '#contact', 'primary')(aria-label='Open contact')` + вкладений `+icon('mail', 14)`.

### 7. Чим `//` відрізняється від `//-` у Pug? Як задати клас за умовою?

- `//` створює **публічний HTML-коментар** (`<!-- ... -->`), який потрапляє у фінальний `dist/index.html`.
- `//-` створює **службовий (буферизований) коментар Pug**, який залишається лише у вихідному коді й не потрапляє у згенерований HTML.
- Клас за умовою задається через об'єкт у атрибуті `class`: `a.nav__link(class={ 'nav__link--active': item.active })`.

### 8. Чому `@import` у Sass застарів? Чим `@use` відрізняється від `@forward` і що таке partials?

- `@import` завантажував усі змінні та міксини у глобальний простір імен (викликаючи конфлікти імен) і повторно компілював один і той самий файл при кожному імпорті.
- `@use` підключає модуль один раз і створює для нього локальний простір імен (наприклад, `math.div()` або `abstracts.$colors`).
- `@forward` реекспортує члени одного модуля назовні через індексний файл (`_index.scss`), щоб інші файли могли підключити всю папку одним рядком `@use '../abstracts' as *`.
- **Partials** — допоміжні SCSS-файли, ім'я яких починається з підкреслення (`_variables.scss`); Sass не компілює їх в окремі `.css`-файли напряму.

### 9. Як у вашому міксині медіазапитів реалізовано підхід mobile first? Чому значення брейкпоінтів зберігаються в map-і?

- У `src/styles/abstracts/_breakpoints.scss` базові стилі пишуться для мобільних екранів без медіазапитів, а міксин `@mixin mq($bp)` використовує умову `@media (min-width: map.get($breakpoints, $bp))`.
- Зберігання брейкпоінтів у SCSS-мапі (`$breakpoints: ('md': 768px, 'lg': 1280px)`) дає єдине джерело істини, виключає «магічні числа» у компонентах і дозволяє валідувати ім'я точки через `map.has-key()`.

### 10. Чим змінні Sass (`$var`) відрізняються від CSS custom properties (`--var`)? Чому в роботі використовуються обидва види?

- Змінні Sass (`$var`) існують **лише під час компіляції** — у готовому CSS замість них підставляються статичні значення. Вони потрібні для обчислень, циклів `@each`, мап і міксинів (`@media` не підтримує `var()`).
- CSS custom properties (`--var`) працюють **у браузері в реальному часі (runtime)**, успадковуються по DOM і можуть змінюватися в медіазапитах (наприклад, `--section-space` змінюється на `768px` і `1280px` без дублювання правил у компонентах).

### 11. Чому важливо обмежувати вкладеність у SCSS? Як `&__` і `&--` допомагають дотримуватися БЕМ?

- Надмірна вкладеність роздуває розмір CSS-селекторів, підвищує специфічність (що змушує писати `!important`) і жорстко прив'язує стилі до структури HTML.
- Конструкції `&__element` та `&--modifier` усередині `.block { ... }` генерують плоскі селектори з низькою специфічністю (`.block__element`, `.block--modifier`), зберігаючи при цьому візуальну групованість коду одного БЕМ-блоку.

### 12. Що таке PostCSS і як Vite його підключає? Як Autoprefixer дізнається, які префікси додавати?

- **PostCSS** — інструмент для перетворення CSS за допомогою JS-плагінів на рівні абстрактного синтаксичного дерева (AST). Vite має вбудовану підтримку PostCSS і автоматично підхоплює конфіг `postcss.config.js` у корені проєкту.
- **Autoprefixer** читає файл `.browserslistrc` (або поле `"browserslist"` у `package.json`), звіряється з базою даних **Can I Use** і додає лише ті вендорні префікси (`-webkit-`, `-moz-`), які потрібні для вказаних версій браузерів.

### 13. Що Vite робить із CSS без жодних налаштувань? Чому у Vite-проєкті не потрібен `cssnano`, але потрібен `Autoprefixer`?

- Без додаткових плагінів Vite вміє компілювати `.scss` (за наявності пакета `sass`), вбудовувати `@import`, переписувати шляхи у `url()`, додавати контент-хеші до імен файлів (`main-a1b2c3.css`) та мініфікувати CSS при збірці через `esbuild`.
- Окремий мініфікатор `cssnano` не потрібен, бо `esbuild` уже стискає CSS за замовчуванням (`build.cssMinify: true`). А **Autoprefixer** потрібен обов'язково, оскільки `esbuild` не читає `.browserslistrc` і додає префікси лише для мінімального набору властивостей.

### 14. Порівняйте JPEG, PNG, WebP, AVIF і SVG. Чому в `<picture>` джерело AVIF стоїть перед WebP?

- **JPEG** — растровий формат із втратами для фотографій без прозорості.
- **PNG** — растровий формат без втрат із підтримкою альфа-каналу (важкий для фото).
- **WebP** — сучасний формат від Google, на 25–35% легший за JPEG/PNG, підтримує прозорість і анімацію.
- **AVIF** — найновіший формат на базі кодека AV1, забезпечує найкраще стиснення (на 40–50% легший за JPEG) при високій деталізації.
- **SVG** — векторний XML-формат для логотипів та іконок, масштабується без втрати якості.
- Браузер обирає **перший** `<source>` у `<picture>`, формат якого він підтримує. Тому найлегший **AVIF** ставлять першим, далі **WebP**, а в кінці — універсальний `<img>` (JPEG) як fallback.

### 15. Як браузер обирає зображення за `srcset` і `sizes`? Навіщо `<img>` атрибути `width` і `height`?

- За атрибутом `sizes` браузер обчислює, яку реальну ширину на екрані займатиме картинка при поточній ширині вікна, множить її на щільність пікселів екрана (`devicePixelRatio`, наприклад `2x` для Retina) і обирає зі списку `srcset` (`400w`, `800w`) найбільш підходящий файл за шириною.
- Атрибути `width` і `height` дозволяють браузеру заздалегідь обчислити співвідношення сторін (`aspect-ratio`) і зарезервувати місце на сторінці ще до завантаження файлу, запобігаючи стрибкам верстки (**CLS — Cumulative Layout Shift**).

### 16. Коли використовувати `loading="lazy"`, а коли `fetchpriority="high"`?

- `loading="lazy"` використовується для зображень **нижче першого екрана** (картки портфоліо, прев'ю журналу), щоб браузер завантажував їх лише при прокручуванні сторінки.
- `fetchpriority="high"` (без `lazy`) ставиться на головне зображення **першого екрана (LCP)**, щоб браузер завантажив його з максимальним пріоритетом одразу при відкритті сторінки.

### 17. Чим Prettier відрізняється від Stylelint? Чому стандартне правило `selector-class-pattern` довелося змінити?

- **Prettier** відповідає виключно за **форматування коду** (відступи, лапки, переноси рядків, пробіли).
- **Stylelint** — це **статичний аналізатор (лінтер)** для CSS/SCSS, який шукає логічні помилки, заборонені конструкції (`!important`, `#id`), надмірну вкладеність і порушення іменування класів.
- Стандартне правило `selector-class-pattern` у `stylelint-config-standard-scss` дозволяє лише `kebab-case` (одинарні дефіси) і блокує подвійні підкреслення `__` та подвійні дефіси `--`, тому його замінили на регулярний вираз для **БЕМ** (`block__element--modifier`).

### 18. Що таке Git hooks? Навіщо поєднувати `husky` і `lint-staged` і чому хук не замінює перевірку в CI?

- **Git hooks** — скрипти, які Git автоматично запускає при певних подіях (наприклад, `pre-commit` перед створенням комміту).
- **husky** керує встановленням хуків у репозиторії, а **lint-staged** запускає лінтери лише на тих файлах, які додані в поточний комміт (`git add`), що працює миттєво.
- Локальний хук можна обійти прапорцем `git commit --no-verify` або вимкнути локально, тому фінальна перевірка в **CI (GitHub Actions)** залишається обов'язковим захисним бар'єром.

### 19. Навіщо у `vite.config.js` параметр `base` під час публікації на GitHub Pages?

- На GitHub Pages проєктний сайт публікується не в корінь домену (`/`), а в підкаталог з назвою репозиторію: `https://staassh.github.io/landing-keepsake-vite/`.
- Параметр `base: '/landing-keepsake-vite/'` вказує Vite додавати цей префікс до всіх згенерованих шляхів до JS, CSS та асетів під час `npm run build`, інакше браузер шукатиме їх у корені домену й отримає помилку `404`.
